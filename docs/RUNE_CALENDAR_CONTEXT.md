# Календарный контекст рун — v1

Дата реализации: 25.10.2026. Модуль `dis_oracle.calendar_context` связывает
руническую карточку с традиционными оценками календарного дня. Сохраняются
исходные данные, источники, часовой пояс, версия правил и хеш снимка.

## Подключённые профили

| Профиль | Что рассчитывается | Обязательные данные |
| --- | --- | --- |
| `japanese_rokuyo` | Шесть меток рокуё по заявленной японской лунной дате | Номер лунного месяца и дня, признак вставного месяца, источник соответствия современной дате |
| `egyptian_cairo` | Три оценки дня из локального корпуса Каирского календаря | Египетский месяц/день, явное современное соответствие и его источник, локальный корпус |

Профиль `{}` означает «запрошено, но данных нет» и возвращает `ABSTAIN`.
Неполный непустой профиль отклоняется. `status=OK` означает корректно выполненный
условный расчёт; `source_verification=USER_DECLARED` и `forecast_status=ABSTAIN`
сохраняются. Программа не удостоверяет истинность указанного источника.

### Японское рокуё

Источник правил: [Национальная парламентская библиотека Японии](https://www.ndl.go.jp/koyomi/chapter3/s3.html).
Индекс `(lunar_month + lunar_day - 2) % 6` выбирает из последовательности
`Sensho, Tomobiki, Senbu, Butsumetsu, Taian, Shakko`. На новом лунном месяце
отсчёт начинается по его номеру, а не продолжается от предыдущего дня.
Для вставного месяца используется его заявленный номер; самостоятельная
проверка межмесячной астрономической границы отсутствует.

| Метка | Принятая традиционная характеристика |
| --- | --- |
| Sensho | Благоприятное утро, неблагоприятная вторая половина дня |
| Tomobiki | Смешанная оценка, зависящая от занятия и периода дня |
| Senbu | Неблагоприятное утро, благоприятная вторая половина дня |
| Butsumetsu | Общая неблагоприятная оценка |
| Taian | Общая благоприятная оценка |
| Shakko | Смешанная: неблагоприятный день с оговоркой о полудне |

Приведено обобщение выбранного источника: интерпретации различаются. Метки не
универсальны для всех занятий. Точные часовые интервалы не назначаются.
[NAOJ предупреждает](https://www.nao.ac.jp/faq/a0304.html), что современного
официального расчёта японского лунно-солнечного календаря нет. Поэтому модуль
не заменяет японскую лунную дату китайской и не вычисляет её из Gregorian.

### Древнеегипетский Каирский календарь

Основание: Jetsu et al. (2013), *The Astrophysical Journal* 773:1,
[DOI:10.1088/0004-637X/773/1/1](https://doi.org/10.1088/0004-637X/773/1/1),
[авторский PDF, таблица 1 на второй странице](https://www.mv.helsinki.fi/home/jetsu/papers/algol1.pdf).
В таблице 360 календарных позиций; 305 читаемых троек и 55 неизвестных.
`G` означает благоприятную, `S` — неблагоприятную часть дня. `GGG` и `SSS`
дают общую оценку, другие читаемые тройки — смешанную. Неизвестная тройка
возвращает `ABSTAIN`, как и пять добавочных дней (месяц 13, дни 1–5).

Древний день начинался с рассвета. Границы трёх частей неоднозначны; модуль
не подставляет интервалы по восемь часов. Нет автоматического перевода
современной даты в египетскую. `mapping_rule=DECLARED_MODERN_CORRELATION`
означает заявленное пользователем соответствие, а не установленную историческую
корреляцию. `civil_midnight` ниже определяет только современную местную дату
для проверки этого заявления, а не начало древнеегипетского дня.

Полный исследовательский корпус не распространяется с пакетом: у использованной
публикации указано © AAS, а лицензия повторного распространения таблицы отдельно
не установлена. Публичный checkout без локального корпуса выдаёт
`CORPUS_UNAVAILABLE`. Формат локального файла описан в
[data/calendar/README.md](../data/calendar/README.md). Наличие файла не означает
проверку лицензии или исторического соответствия дат программой.

## Вход и запуск

В манифест цикла добавляется необязательный `calendar_context`:

```json
{
  "schema_version": "rune-calendar-context-v1",
  "event_at": "2099-01-01T00:00:00Z",
  "timezone": "Europe/Moscow",
  "day_boundary": "civil_midnight",
  "profiles": {"japanese_rokuyo": {}, "egyptian_cairo": {}}
}
```

`event_at` должен совпасть с одним deadline зарегистрированного события. Все
временные метки содержат смещение UTC. Непустому профилю нужны `calendar_date`
(местная дата события), `source_ref` (HTTP/S), `source_locator` и `available_at`.
Последнее не может быть позже регистрации или cutoff фактов. Часовой пояс — IANA.
Неизвестные поля и логические значения вместо целых чисел отклоняются до RNG.

Примеры полностью **SYNTHETIC**: указанные лунные и египетские даты выбраны для
демонстрации и не объявляются реальными соответствиями 2099 году.

```bash
# Чистый расчёт, без случайности и без создания журнала:
python -m dis_oracle calendar-context examples/calendar_context/input.synthetic.json

# Полный учебный цикл, в новом каталоге состояния:
python -m dis_oracle cycle-start examples/calendar_context/manifest.synthetic.json --directory /tmp/oracle-calendar-demo-v1 --run-id synthetic-calendar-v1
python -m dis_oracle cycle-review examples/v0_3/review.json --directory /tmp/oracle-calendar-demo-v1 --run-id synthetic-calendar-v1
python -m dis_oracle cycle-freeze --directory /tmp/oracle-calendar-demo-v1 --run-id synthetic-calendar-v1
```

Снимок корпуса фиксируется внутри регистрации **до первого обращения к RNG**;
отдельная запись `calendar-context-v1` повторяет этот снимок. После сбоя или
перезапуска используется сохранённая версия, даже если локальная таблица
поменялась. В `status`, исходном и научном отчётах есть `calendar_context`:
`snapshot`, `snapshot_hash`, `rune_binding` с `card_input_hash` и
`procedure_commitment`. При отсутствии рунической карточки привязка — ABSTAIN.

Для старых манифестов новые поля и записи не добавляются. Старые расклады,
ориентации рун, seed `lottery-rune-hash-v2`, контрольная выборка и веса десяти
ядер сохраняются. Календарь не создаёт claims и не участвует в голосовании.

## Проверка гипотезы дальше

Сначала нужен выбранный и зафиксированный способ получения лунных дат и
египетской корреляции. Затем можно заранее зарегистрировать отдельный метод
с календарными признаками и сопоставить его на будущих событиях с прежним
методом и случайным контролем. Учитываются все зарегистрированные события,
включая пропуски. Подбор удачной корреляции по тем же исходам не даёт независимого
доказательства. Текущая реализация проверяет технику и сохранность данных,
а не влияние календаря на вероятность выигрыша.

## Техническая проверка 25.10.2026

`python -m unittest discover -q`: 196 тестов PASS, включая 24 календарных и 9
интеграционных. Оба прежних офлайн-аудита (`audit_four_qwen.py --check` и
`yijing_audit.py --check`) совпали с сохранёнными результатами. Wheel собирается
без новых зависимостей; его установленная копия прошла чистый CLI-расчёт и полный
синтетический цикл с повторным запуском. Отдельная локальная проверка корпуса
сверила 360 позиций: 177 благоприятных, 105 неблагоприятных, 23 смешанных и 55
неизвестных. Современное соответствие дат в проверках было синтетическим.

Ветка основана на `codex/four-core-audit-v0.3` (5e8fd569), как и существующие
локальные опыты. Более новая `codex/lottery-series-registry` не объединялась:
перенос календаря в её `lottery_plan` потребует отдельной интеграционной проверки.
